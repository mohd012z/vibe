# P17 8-to-7 BitEncoding — real-compiler verification (v0.23, PR #12)

Date: 2026-10-02 · Branch: feat/p17b-real-r8 (PR #12) · Author: Aliph
(Anam-directed "contineu pending" sweep; repair of PR #12 mid-task)

## Gap this closes

P17's disclosed limit: **8-to-7 BitEncoding mode "implemented but not
exercised by a real sample."** The committed fixture (`tests/fixtures/
ktmeta/classes.dex`) is UTF-8 mode (the default). The 8-to-7 branch of
`bitencoding_decode` had never been validated against the real compiler, and
the module docstring *mis-stated* the mode (marker "U+00FF" — wrong; and it
implied the marker is always present). This round fetched the authoritative
JetBrains `BitEncoding.java`, forced the real compiler into 8-to-7 mode, and
differentially verified the pure Python decoder against the compiler's own
`decodeBytes`.

## Authoritative source (fetched 2026-10-02, Apache-2.0, not memory)

`core/metadata.jvm/src/org/jetbrains/kotlin/metadata/jvm/deserialization/
BitEncoding.java` + `utfEncoding.kt`. Key facts the real source established:

- `decodeBytes` has exactly **TWO** modes. First char `U+0000`
  (`UTF8_MODE_MARKER`) → UTF-8; **everything else → 8-to-7.** There is **no
  third "raw char→byte" fallback** (my decoder invented one — the bug below).
- 8-to-7 is **gated by a JVM property**: `FORCE_8TO7_ENCODING =
  "true".equals(System.getProperty("kotlin.jvm.serialization.use8to7"))`,
  read in a **static initializer** (class-load), so it is OFF by default and
  settable only via `-Dkotlin.jvm.serialization.use8to7=true` on the `java`
  command line — flipping the `static final` field by hand in `main` is too
  late (initializer already ran).
- The 8-to-7 **mode marker is `U+FFFF`** (not U+00FF), and it is **only
  prepended to the first string when the payload SPLITS** (input ≥ ~65533
  effective bytes, `splitBytesToStringArray`). For the common **small**
  payload there is **NO marker char** — `d1[0]` is real data (a
  modulo-incremented 8-to-7 byte, `U+0001..U+0080`).
- **8-to-7 is lossy on a lone high byte.** The compiler's OWN `decodeBytes`
  roundtrip of a single `0x7f` returns `0x01`, of a single `0xff` returns
  `0x02` (RT0). A faithful port MUST match the compiler's decode, not the
  original bytes — which is exactly what the differential asserts.

## The real bug found (evidence, not guess)

The pure decoder's `bitencoding_decode` had a third branch:
`if no known mode marker: raw char→byte (no drop)`. Against the real
compiler's `encodeBytes`/`decodeBytes` (both modes, 8 cases incl. no-marker
small, `U+FFFF` multi-part, and the lossy lone-byte cases) the **old** code
mismatched the compiler on **6/20** cases — precisely the no-marker 8-to-7
path. The corrected decoder (drop `U+FFFF` if present, else use the whole
string; `raw = (char-1)&0x7f`; `decode7to8`) matches the compiler's decode
on **all 20**. The docstring's wrong "U+00FF / always-marked" text was also
corrected.

## What was built

- `tools/vibebot/BE8to7.java` — differential oracle (subprocess over
  kotlin-compiler.jar, same license-safe pattern as `KMeta.java`): for each
  byte case it runs the compiler's `encodeBytes` (8-to-7 forced via the
  authoritative `-D` flag) and `decodeBytes`, emitting the d1 (2-hex-per-char,
  lossless, unambiguous — a raw char-escape breaks when data contains `0x5C`
  `\`) + the decode hex (the oracle). `BIG:<n>` synthesizes a large in-process
  case so the multi-part `U+FFFF` split is exercised without a 140KB argv.
- `kotlinmeta.py`: `run_be8to7_oracle(hex_cases, mode, workdir)` +
  `_find_be8to7_verifier` + `_hexchars_to_str`; fixed `bitencoding_decode`
  (removed the invented raw fallback; correct `U+FFFF`/no-marker handling) +
  corrected the module docstring's mode description.
- `vibebot_test.py`: real-compiler 8-to-7 differential in BOTH modes (utf8 +
  8to7, 8 cases each), a "mode is REAL" guard (no `U+0000` on the no-marker
  small case), a "BIG case carries the `U+FFFF` marker" guard, and a unit
  test pinning no-marker 8-to-7 (replacing the old test that asserted the
  removed raw fallback). Degrades to honest NOT OBSERVED when the Kotlin
  toolchain is absent (CI-shape stays green).

## Real gotchas (not guessed)

- The `static final` flag can't be flipped from `main` (class-load timing) —
  must use the `-D` system property.
- Java source cannot contain `\uXXXX` in a **comment** (it's a unicode
  escape, breaks compilation) — reworded.
- Hex seeds must be valid hex — `0x5EED8to7` is not (a typo that reads like a
  word). Use `0x5EED8207L`.
- Char-escape transport of d1 is ambiguous when data contains `\`; hex-per-char
  is lossless for a Java `char` (0..65535).
