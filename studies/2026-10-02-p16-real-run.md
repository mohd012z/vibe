# P16 real-run — E5 harness executed on a real aarch64 toolchain (v0.21, PR #6)

Date: 2026-10-02 · Branch: feat/native-r2-verified (folded) · Author: Aliph (Anam-directed "contineu pending" + explicit proceed/approval)

## Gap this closes

P16 (native-harness validation) is the **top of the evidence chain**: prove a
native (ARM64) change *behaves* — E5 runtime, "never 'the diff looks right'".
Up to now its `validate_native`/`HarnessEngine` had only ever run through a
`FakeRunner`; on this x86_64 host the real path was an honest NOT OBSERVED
(no cross-compiler, no qemu). That is the last "no toolchain on host" gap in
the whole /360 roadmap after P18 (x86-64 r2), P19 (aarch64 disasm), P14b
(real hybrid APK).

## Toolchain installed (user-space, scratch — no root)

Host has no root (uid 10000), so Debian trixie debs were resolved with
`apt-get --print-uris`, filtered to the cross-toolchain closure (systemd/dbus/
dmsetup/kmod noise dropped), and extracted to
`/opt/data/cache/scratch/toolchain/cross16/` via `dpkg -x`:

- `gcc-aarch64-linux-gnu` / `gcc-14-aarch64-linux-gnu` / `cpp-14-…` →
  `aarch64-linux-gnu-gcc` (the real cross **cc**)
- `binutils-aarch64-linux-gnu` (as — also present from P19)
- `qemu-user` → **`qemu-aarch64`** (user-mode emulator; host is x86_64 so
  `needs_qemu=True`)
- `libc6-arm64-cross` + `libc6-dev-arm64-cross` + `linux-libc-dev-arm64-cross`
  → the `/usr/aarch64-linux-gnu` **sysroot** the harness runs qemu against
  (`qemu-aarch64 -L /usr/aarch64-linux-gnu tests`)

The harness recipe is **exercism-arm64 verbatim** (NOT hand-rolled, per the
P16 spec): `CFLAGS = -g -Wall -Wextra -pedantic -Werror -std=c99 -fPIE`,
`LDFLAGS = -pie -Wl,--fatal-warnings`, run under `qemu-aarch64 -L <sysroot>`.

## The real run

`tests/fixtures/harness/popcount.c` — a small, real C harness: a
**Kernighan popcount** (the same idiom P15's classifier recognizes statically)
as the function-under-test, plus a `main()` that runs 6 assertions and prints
`6 passed, 0 failed` — the exact shape `parse_harness` expects. Built at test
time by the P16 real-e2e block via the real `aarch64-linux-gnu-gcc` +
`qemu-aarch64`.

Result on the real toolchain:
- compile: `aarch64-linux-gnu-gcc -g -Wall -Wextra -pedantic -Werror
  -std=c99 -fPIE -c …` → ok
- link: `… -pie -Wl,--fatal-warnings -o tests c0.o` → ok (real PIE aarch64
  ELF)
- run: `qemu-aarch64 -L /usr/aarch64-linux-gnu tests` →
  `PASS: popcount(0/1/0xff/0x80000000/0x55555555/0xffffffff)` +
  `6 passed, 0 failed` → **verdict SUCCESS, E5 runtime**

This closes the loop **P15 (static, E3) → P16 (runtime, E5)** on a real
build: the popcount idiom the classifier flags is proven to *behave* under
qemu.

## Test added

`tools/vibebot_test.py` — P16 block, a new REAL e2e after the existing
FakeRunner e2e + honest-degrade checks. Self-guarding: when the cross gcc or
qemu is absent it prints an honest NOT-OBSERVED line (never a red check), so
CI shape stays green. Three new checks (SUCCESS+6-passed, final command is
`qemu-aarch64 -L`, E5 ceiling note). The block runs the subprocess under a
child **env PATH** that includes the scratch toolchain dirs — it does NOT
modify the shell PATH, so the earlier P16 `detect_providers()`-independent
checks and the P6 "native providers absent" assertion are untouched.

## Bugs the real run exposed (the FakeRunner never hit these)

1. **`build_cmd_link` / `run_cmd` never received the sysroot** (TDD caught):
   threading `--sysroot` through `build_cmd_c` alone is not enough — the
   link still used the baked-in `/usr/aarch64-linux-gnu` sysroot and failed
   with `cannot find /usr/aarch64-linux-gnu/lib/libc_nonshared.a`; and the
   qemu run with the default `-L /usr/aarch64-linux-gnu` failed with
   `Could not open '/lib/ld-linux-aarch64.so.1'`. All three stages
   (compile, link, run) now take the same `sysroot` (default `None` keeps
   the exercism-verbatim command byte-identical for normal installs).
2. **A user-space extract must be a SELF-REFERENTIAL sysroot**: the
   aarch64 cross-ld has `/usr/aarch64-linux-gnu` compiled in; passing
   `--sysroot <extract-root>` only works if `<extract-root>/usr/aarch64-
   linux-gnu/lib` holds the glibc (it does, from `libc6-dev-arm64-cross`)
   AND `<extract-root>/lib` resolves for qemu's interpreter lookup
   (the test block self-creates the `lib -> usr/aarch64-linux-gnu/lib`
   symlink idempotently — a fresh re-extract would lose it).
3. **The cross gcc's internal as/ld are shared-lib builds** needing
   `LD_LIBRARY_PATH=<extract>/usr/lib/x86_64-linux-gnu`
   (`libbfd-2.44-arm64.so` / `libopcodes-2.44-arm64.so`) — same trap as
   P19's binutils extract; the test block sets it in the child env.

## Honest limits

- `qemu-aarch64` is **user-mode** emulation: it proves the aarch64 binary's
  *behavior* (the test's observable contract), not performance, and not
  kernel/privileged paths. E5 ceiling as always: "proves THIS build passes
  THIS test, not that the change is generally correct."
- One function-under-test (popcount); the harness itself is the same
  `validate_native` path any C/asm change would take. A richer corpus (e.g.
  the P15 idioms as C functions) is a natural extension, not a correctness
  gap.
- The cross sysroot is Debian trixie glibc 2.41; a change targeting a
  different libc/bionic would need that sysroot (out of scope — the recipe is
  injectable via `toolchain=`).
